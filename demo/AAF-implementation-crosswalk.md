# Accountable Agents Framework implementation crosswalk

The reference implementation in `AAF_OSFI` combines mailbox-control proofing, passkeys, request-bound agent signatures, on-demand IDs, Directory-attested authorization, a signed status list, and Directory-held identity escrow. This table maps those choices to Appendix C of the paper and shows the alternatives the paper leaves open. [Appendix A conformance notes](../docs/CONFORMANCE.md) track requirements separately.

**Basis.** Appendix C, pp. 20–24 of [the working paper](2026_11_20_Accountable_Agents.pdf). This compares the [earlier proposal](PROPOSAL-reference-implementation.md#3-design-choices-the-simplest-option-in-each-of-the-papers-tables) with `AAF_OSFI` main at `8bdac3e`. The [deployment record](log.md#2026-11-22-0950-pst--live-on-the-web-ready-for-owner-uat) identifies `2b7c846` as the hosted service image. The comparison of those revisions shows one runtime change, the local agent's recovery of a previously approved pairing. The service-side choices below apply to both revisions.

| Paper component | Current pilot | Other options in the paper |
|---|---|---|
| **C §1. Identity proofing** (PV-1, PV-2) | **Option 4, email.** The hosted Directory sends a single-use invitation through Resend. Redemption attests mailbox control at low assurance. Links supplied by the operator and local stand-ins carry no mailbox assurance. The Directory allows one record per trimmed, lowercased address (PV-3). An individual can still use multiple addresses. | Control of a domain (1), human identity proofing (2), legal-entity and representative proofing (3), or phone control (the other form of 4). The pilot does not use the proposal's stretch option for domain proofing. |
| **C §2. Principal and agent authentication** (PV-5, AG-1, AG-5) | The person uses WebAuthn with user verification and a fresh assertion bound to the displayed action. The agent uses **Option 1**, signing with Ed25519. At the Shop, the proof binds the request and presented credentials to the intended recipient and a single-use Shop nonce. Registration binds the agent's key to the principal after the code and fingerprint match. | Connection-bound proof such as mutual TLS (2), a key kept in certified hardware (3), or zero-knowledge proof of possession (4). The app does not establish that agent keys are non-exportable. |
| **C §3. IDs and presentations** (PR-1, PR-2, PR-5, PR-6, PR-7) | **Option 1.** The Directory issues on demand. The default presentation uses a fresh random identifier, a fresh key and a five-minute lifetime. The agent requests claims as needed. The Directory sees the counterparty, timing and requested claims. Presentations within the same operation share an operation ID, and simultaneous revocations can expose correlations. | Batches of single-use credentials with selective disclosure (2), or anonymous credentials with fresh proofs (3). A zero-knowledge design still needs a way to recover the verified identity under ES-1. |
| **C §4. Authorizations** (PR-4, PR-10, RV-1) | **Options 1 and 2.** The Directory attests to the principal's standing grant and, when requested, confirms passkey approval of an exact transaction. The approval is bound to the Shop, action and grant version. For the demo Shop, orders above $50 require exact-action approval even inside the standing grant. The Shop asks for additional claims before the agent requests them from the Directory. | A principal-signed mandate using a key outside the agent's reach (3), or an agent's self-asserted scope (4). The Shop does not accept a self-assertion as proof of the principal's authority. |
| **C §5. Validity and revocation** (PR-3, PR-9, RV-1, RV-2) | **Option 3 with a short credential lifetime.** The Directory publishes a signed whole-list snapshot. The Shop refreshes it without asking the Directory about a particular ID. The default publication and fetch intervals are five seconds. The published budget is 30 seconds (10 for publication, 18 for accepted list age, 2 for clock skew). The Shop defers an action if its status evidence is stale. | Short-lived IDs with no status check (1), stapled signed status (2), or a compact proof of non-revocation (4). The 15-second interval in the proposal was superseded. |
| **C §6. Identity escrow** (ES-1, ES-2) | **Option 1.** The Directory stores each issuance with the agent and principal. The Shop supplies a signed report and receipt for that issuance. An operator records the basis and confirms the simulated release with a passkey. The case and release survive revocation, and the principal sees both notices. | An encrypted pointer in the presentation (2), or a split map or key requiring several parties to cooperate (3). In this pilot one Directory holds the mapping. |
| **C §7. Pairwise agent identifiers** (PR-8) | **Option 1, available on request.** The Directory derives a stable identifier for the agent and Shop from the agent record and the Shop origin. Repeated use of that mode lets the Shop link those visits. The main demo uses the default fresh IDs. | An agent-derived, provable pairwise identifier using a Directory-attested secret (2). The pilot has no principal-level pairwise identifier. |
| **C §8. Directory key management** (DR-1) | One online Ed25519 signing key is stored by the Directory. Its published practices explain how the key is handled. | Certified hardware (1), an offline root with replaceable online keys (2), or scheduled key retirement (3). These are approaches the pilot does not exercise. |
| **C §9. Arrangements among directories** (PV-4, DR-3) | The Shop has an explicit list of trusted Directory origins. This is the Shop's own configuration. It has no cross-directory duplicate check or independent conformity assessment. | A published shared trust list with membership rules (1), cross-directory duplicate checks (2), or an audit or certification against a common standard (3). |

**Standards examples.** The paper lists OpenID Connect ID tokens as a precedent for on-demand issuance and cites its pairwise subject identifiers. It lists **OAuth scopes** for standing authorization and **OAuth Rich Authorization Requests** for transaction-specific authority. This build demonstrates those design choices with its own signed credentials, requests and approvals. It does not implement an OpenID Connect or OAuth flow. [Protocol guide](../docs/PROTOCOL.md)

## What the demo verified

- **Hosted owner UAT.** A real invitation arrived by email and was redeemed. The owner used Mac passkeys for enrollment, pairing, one exact order, grant withdrawal, agent revocation, and the simulated operator release. The Shop still gave a quote after grant withdrawal. After agent revocation, the Directory refused a new ID. The Shop rejected the older credential as expired. [Owner UAT review](UAT-review.md)
- **Isolated local rehearsal.** The browser test passkey and local invitation were stand-ins. This run additionally observed the Shop reject a previously issued, still-unexpired ID as revoked. It also verified the incident and release notices referred to the same case. [Rehearsal results](codex-illustrated-demo/captures/result.json)

These observations show the pilot mechanisms under the recorded conditions. The Appendix A table carries the separate limitations, including partial unlinkability and the absence of independent conformity assessment.
